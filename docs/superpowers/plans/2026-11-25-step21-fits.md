# ステップ21：制度と会社の相性（仕組みと効き目） Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 職種と業種に性質の印を付け、`src/data/fits.json` の相性21個が、条件に合う会社・社員に効くようにする（兆しのイベントはステップ22、振り返りの説明はステップ23）。

**Architecture:** `src/engine/fits.ts` が、その月の会社の状態から「効いている相性」を求め（`fitsFor(state)`）、社員ごとの効き目（要因の点数・評価のずれ・立ち上がり・実力の伸び・辞めやすさ）と会社の効き目（費用・割増の付く残業・採用のしにくさ・等級の運用コスト）を返す。tick が月のはじめに1回求め、今ある差し込み口に省略可能な引数 `fits` で渡す（省略すると今までどおり＝既存のテストは変わらない）。

**Tech Stack:** TypeScript、Vitest、既存の係数台帳とデータの形（`Sourced`）

**Spec:** `DESIGN.md` §14.8（相性の一覧と性質の印）

## Global Constraints

- `src/engine/` は React に依存させない。乱数は使わない（相性は決まった計算）
- 効き目の数値はすべて `fits.json` に `Sourced`（`value`・`unit`・`basis`・`source`）で置く。目安（30人など）は係数台帳 `fit.*`
- 相性 11・12・21 は効き目を持たない（説明だけ。ステップ22・23で使う）
- セーブの形式は変えない（このステップでは状態に何も足さない）
- テストは「制度を変えると、当てはまる社員の結果が決めた方向に動く」と「当てはまらない社員には効かない」を相性ごとに確かめる

## Review Focus

1. 当てはまる社員が0人の会社（SaaS 以外のエンジニアなど）→ 相性は効かず、落ちない
2. 印のない職種や、古いセーブの社員（`hireChannel` が `founding`）→ 条件に合わないだけで落ちない
3. 2つの相性が同じ要因に効く（1 と 19 はどちらも「社内の公平さ」）→ 足し合わせ、点数は0〜100に収まる
4. 評価のずれの倍率が重なる（2・5・10・20）→ 掛け合わせても上限（`policy.evaluation.max_noise`）を超えない
5. 社員数がちょうど目安（30人）のとき → 「未満」で判定（30人は小さい会社ではない）

## データの形

`src/engine/types.ts` に足す：

```ts
export const ROLE_TRAITS = ['team', 'synchronous', 'shift', 'hardToQuantify', 'marketPriced', 'storeManager', 'skilled'] as const;
export type RoleTrait = (typeof ROLE_TRAITS)[number];
export const INDUSTRY_TRAITS = ['peaks'] as const;
export type IndustryTrait = (typeof INDUSTRY_TRAITS)[number];
// RoleData に traits?: RoleTrait[]、IndustryData に traits?: IndustryTrait[]

export type FitTone = 'good' | 'bad';
export type FitWhen = {
  /** どれか1つの組（制度カテゴリ→選択肢の候補）に合えばよい */
  policiesAny?: Partial<{ [K in keyof PolicySet]: PolicySet[K][] }>[];
  industryTraits?: IndustryTrait[];
  /** 業種の景気の波がこの係数（id）以上 */
  cyclicalityAtLeast?: string;
  /** 社員数がこの係数（id）未満 */
  headcountBelow?: string;
  /** 社員数が管理職1人の見られる人数を超えた */
  headcountAboveSpan?: boolean;
  locationType?: LocationType;
  foundingPatterns?: FoundingPatternId[];
  orgForms?: OrgForm[];
  /** 直近12か月に赤字の月がある */
  recentLoss?: boolean;
  /** 子会社で出向者がいる（どの職種かは who で見る） */
  hasSecondees?: boolean;
};
export type FitWho = {
  /** どれかの印を持つ職種 */
  roleTraits?: RoleTrait[];
  /** 印の代わりにパートでも当てはまる（360度評価×パート） */
  orPartTime?: boolean;
  employmentTypes?: EmploymentType[];
  hireChannels?: HireChannel[];
  maxTenureMonths?: number;
  affiliation?: Affiliation;
  /** 同じ職種に出向者がいるプロパー社員 */
  sameRoleHasSecondee?: boolean;
};
export type FitEffects = {
  factors?: Partial<Record<EngagementFactor, Sourced<number>>>;
  evaluationNoiseMult?: Sourced<number>;
  rampMult?: Sourced<number>;
  abilityGainMult?: Sourced<number>;
  attritionMult?: Sourced<number>;
  costPerEmployee?: Sourced<number>;      // 当てはまる社員1人あたり（円/月）
  premiumOvertimeMult?: Sourced<number>;  // 会社全体
  hiringDifficultyMult?: Sourced<number>; // 会社全体
  gradeCostMult?: Sourced<number>;        // 会社全体（等級の運用コスト）
  cancelGrowthBonus?: boolean;            // 等級の「成長の機会」の上乗せを消す（会社全体）
};
export type FitDef = {
  id: string; no: number; name: string; tone: FitTone;
  when: FitWhen; who?: FitWho;
  /** 制度の選択肢ごとの効き目の強さ（例：ハイブリッド0.5・在宅1） */
  scale?: { category: keyof PolicySet; byOption: Partial<Record<string, number>> };
  effects: FitEffects;
  /** 根拠（相性そのもの） */
  basis: Basis; source: string;
  /** 効き目のない、説明だけの相性（11・12・21） */
  explainOnly?: boolean;
};
```

効き目の強さは「1＋(倍率−1)×scale」「点数×scale」で弱める。

### Task 3: 効き目をエンジンに差し込む

**Files:** Modify `engagement.ts`（`EngagementContext.fits?`。`computeFactorScores` の上乗せに足す）、`evaluation.ts`（`evaluate` の ctx に `fits?`。ずれを社員ごとの倍率にし、上限は `policy.evaluation.max_noise`）、`policies.ts`（`rampParams` と `annualAbilityGain` に倍率の引数を省略可能で足す、`growthBonus` を消す指定）、`performance.ts`・`attrition.ts`・`finance.ts`・`hiring.ts`（倍率と費用）、`tick.ts`（月のはじめに `fitsFor(state)` を1回求めて渡す）。Test `src/engine/fits.effects.test.ts`

- [ ] テスト（相性ごとに、同じ会社で制度だけ変えて比べる。乱数を使わない関数のレベルで確かめる）：
  - 1：給与を成果連動にすると、飲食の店舗スタッフの社内の公平さが下がり、本部は変わらない
  - 2：評価が社長のまま在宅にすると、評価のずれが大きくなる（在宅＞ハイブリッド）。評価を MBO にすると付かない
  - 3：フレックスにしても、製造の製造職の働く負荷は上がらない（事務・品質管理は上がる）。費用が増える
  - 4：変形労働時間制で、飲食の割増の付く残業が商社より大きく減る（良い相性）
  - 5：MBO で、事務のずれだけ大きくなる
  - 6：職能資格で、SaaS のエンジニアの社外と比べた給与と成長の機会が下がり、営業・CS は変わらない。7：相場連動でエンジニアの社外と比べた給与が上がる
  - 8：在宅で、新卒2年未満の立ち上がりが遅くなる。中途は変わらない
  - 9：29人で役割等級だと等級の運用コストが高く、成長の上乗せがない。30人では効かない
  - 10：360度評価で、飲食のパートと店舗スタッフのずれが大きく、費用が増える
  - 11・12・21：効いても効き目は中立
  - 13：新卒中心・29人で、新卒36か月未満の辞めやすさが上がる
  - 14：特別条項で、飲食の店長の働く負荷が下がり辞めやすくなる（月45時間は半分）
  - 15：育成投資ありで、パートの実力の伸びが正社員より小さい
  - 16：中途中心で、製造の中途24か月未満の立ち上がりが遅い
  - 17：地方で在宅にすると採用のしにくさが下がる。都市では変わらない
  - 18：業績連動賞与で直近に赤字があると雇用の安定が下がる
  - 19：子会社で出向者のいる職種のプロパーの社内の公平さが下がる
  - 20：マトリクスで社長評価のずれが大きく、360度評価では付かない
  - 上限：ずれの倍率が重なっても上限を超えない。要因の点数は0〜100
  - tick：`fits` を渡さない既存の関数の呼び方では結果が変わらない（既存のテストがすべて通る）
- [ ] 落ちる → 実装 → 通る → `npm test` 全体 → commit「ステップ21：相性の効き目をエンジンに」
